# 开发流水线（强制关口·通用核心）

## 入口判断

- 新需求（PRD / 原型 / 口头功能描述要开发）→ 走 G1-G6
- 缺陷 / 异常行为 → 走 B1-B3
- 一句话且信息完整的小改动（改文案 / 调样式）→ 不走关口，直接做
- 分不清 → 先问用户

每个关口的产物须用户 review 通过才进下一关。【禁止跳关、禁止合并关口、禁止关口产物只停留在对话里不落盘。】

## 仓库适配

本 skill 是通用核心。文中「仓库规范」指当前仓库根目录 `AGENTS.md` / `CLAUDE.md` 的对应内容（编码规范、构建命令、接口文档要求、自查清单、镜像仓库同步要求等）；仓库没有约定的，按业界常规执行并在产物里注明所采用的口径。

## 子 agent 入场规则

子 agent 买到的是全新视角（无偏差、无沉没成本），代价是从零重读代码库。因此只在**判断类**任务入场，**状态积累类**任务不入场（证据与上下文要留在主会话）：

- **入场**：G3 实现者冷读、G6 整体审查
- **不入场**：G4 逐切片实现（默认主会话内联；仅当需求长到后段会跑在压缩后的上下文上，经用户同意才切「子 agent 逐任务实现 + 进度台账续接」）、B1 调查（证据链留在主上下文）、G1（对话对象是用户）

无子 agent 能力的环境按「自己换视角冷读一遍」降级执行。

## 新需求 G1-G6

### G1 需求澄清

读 PRD / 原型，并搜索现有实现，按 `templates/clarify.md` 产出疑问清单（歧义 / 缺失 / 与现有逻辑冲突 三类，每条附建议默认答案供用户快速拍板）。

大需求（多模块 / 多页 PRD）先回放再提问：每理解一块就用两三百字回放给用户纠正（猜测明确标注为猜测，只有用户说过的才算用户的），问完一块再问下一块，最后汇总成疑问清单。

两条纪律：先让用户描述再给选项（选项会带偏答案）；建议默认答案必须亮给用户（没说出口的默认无法被否决）。

问题预算：清单默认 ≤8 条，按「影响 × 不确定性」排序，只收会实质改变实现或验证方式的问题；纯实现细节不问（留给 G4 裁决）。

【用户未逐条回答前，禁止进入 G2。】

### G2 规格化

按 `templates/spec.md` 产出规格文档（目录从仓库约定，默认 `docs/specs/<需求名>/spec.md`）：用户故事 + 验收标准（EARS 写法：WHEN〈触发〉THE SYSTEM SHALL〈响应〉，**每条带稳定编号 AC1、AC2…**，供 G3 自检与 G5 收敛追溯）+ 字段口径 + 状态流转 + 权限 + 非目标。

写作纪律：G1 澄清答案与 PRD 冲突时以答案为准显式覆盖，不留矛盾表述；术语全文统一；模糊形容词（易用 / 灵活）必须换成可判定指标。

【用户未确认 spec 前，禁止进入 G3。】

### G3 设计（顺序强制：先数据结构后接口）

先搜索现有实现与可复用点（优先复用，不重造），再按 `templates/design.md` 分两步产出，每步单独确认：

1. **表 / 数据结构设计**：DDL 草案（新增 / 变更）→ 用户确认
2. **接口清单**：方法 / 路径 / 职责 / 入出参概要 + 实现任务清单 → 用户确认

设计文档写作标准：**写给一个没见过这个代码库的工程师**——写清「你做的决定」（动哪个文件、什么签名、哪张表、每个接口对应哪个任务），不写泛泛而谈的步骤。

**交付前自检（AI 做，先于交用户）**：

1. G2 spec 验收标准逐条（AC 编号）对应到任务清单，列出无任务对应的条目
2. 接口清单与任务清单一一对应，前后签名 / 字段名一致（前文叫 `clearLayers` 后文变 `clearFullLayers` 就是 bug）
3. 比例检查：设计比 spec 长好几倍即写成了代码转录本，退回「签名 + 决定」级

**实现者冷读（有子 agent 能力时做）**：派一个全新子 agent 只读 spec + 设计文档，以「接下来要动手实现的工程师」视角列出它还得问什么；问题分三堆——已答（答案补进文档）/ 小事（自行拍板并在文档标注为 AI 决定）/ 必须问用户（并入本次确认一次性问完）。

【数据结构未经确认，禁止出接口清单；两者未确认，禁止进入 G4。】

### G3.5 工作量评估（用户要求或排期需要时，不阻塞开发）

按 `templates/estimate.md` 产出简版评估，口径：

- **人 + AI 协作**的工作量（非纯人工口径，AI 提效已计入——纯人工 2 天的 CRUD，人+AI 约 0.5 天）
- 逐功能列条目，粒度 **0.2 ~ 1 天/条**，格式「1. xxx功能 x天」，不搞复杂度矩阵
- 固定 **+1 天缓冲**（防完不成的兜底，给自己留的）
- leader 给了参考时间的注明对照，没给就不写
- **核心输出：预计完成日期**（今天 + 总天数 → 具体日期），这是唯一重要结论
- 评估前查历史 estimate.md 的回填数据校准手感；完工后回填实际天数

### G4 实现（垂直切片，禁止层批量）

任务粒度：**一个 reviewer 能独立否决的最小单元**（即一个接口的一条完整切片），每步是一个可检查的动作。

1. **数据结构落地**：DDL / 迁移脚本写成文件交用户手动执行（AI 不直接改库），ORM 实体 / VO / DTO / 映射全链路同步（按仓库约定）
2. **接口逐个实现**：每个接口走完整垂直切片——数据层 → 服务层 → 接口层 → 接口文档（按仓库规范），完成后立即用仓库约定的构建命令编译验证 + 自查清单，通过再做下一个接口
3. 【禁止】先建完全部实体再铺全部接口、一次性生成一大批接口代码。复杂接口（状态机 / 审批 / 消息 / 金额）必须单个走；同质简单 CRUD 默认也逐个，用户明确说「这几个一起做」才可合并
4. 全程遵守仓库编码规范与最小修改原则

**进度台账**：`docs/specs/<需求名>/progress.md`，每个切片完成即记一行（任务 / 验证证据 / 裁决记录）；会话中断或上下文压缩后凭台账 + git log 续做，不凭记忆（记忆是摘要，台账才是记录）。

**裁决而非停滞**：实现级小冲突（计划笔误、命名不一致、G3 未覆盖的实现细节）自行裁决，台账记 `裁决：<决定>—<理由>—<错了的代价>`，继续做；需求级歧义（口径 / 范围 / 状态流转）仍停下来问用户。只有四类事必停：不可逆 / 破坏性操作、安全敏感动作、仓库外的外部副作用、计划失效到每条路都是猜。G6 汇总时裁决清单必须完整送达用户。

**范围膨胀即停**：中途发现实际范围超出 G2 spec → 停下声明，升档回 G1/G2 重走，不默默扩大。

### G5 收敛检查（验证铁律）

**Iron Law：没有新鲜的验证证据，不得声称任何一项完成。完成声明（任务勾选、台账记录、G4 汇报）都不是证据。**

对照 G2 spec 的验收标准**逐条（按 AC 编号）现场重验**，出差距报告，四类分类：

- **未实现**（missing）：该做的没做
- **实现偏差**（partial）：做了但没满足验收标准
- **与 spec 矛盾**（contradicts）：做了与验收标准相反的——修法与偏差不同，先纠偏再补齐
- **超出范围**（unrequested）：spec 没要求却做了

每条差距挂 AC 编号（unrequested 标注代码位置）；全部满足才报「已收敛」。

| 常见借口 | 现实 |
|---|---|
| 「应该可以了 / 应该没问题」 | 跑验证拿证据 |
| 「代码改了，逻辑上对」 | 编译输出 / 查询结果才算数 |
| 「上个任务验证过了」 | 每个声称都要本次证据 |
| 「台账里记了已完成」 | 收敛时按 spec 全量重验，不认历史声称 |

【未全部通过，打回 G4，禁止进入 G6。】

### G6 提交

代码审查（有 `/code-review` 类命令则跑，否则按审查清单自查）→ 审查发现按「用户实际影响」重定级后分级处置：严重项一次修复完，每个修复带本次验证证据；轻微项只列清单交用户拍板，不顺手修 → 汇总改动、验证结果与 G4 台账的裁决清单（AI 替用户做的决定必须送达）→ **询问用户是否提交 git，不得自行 commit / push**。

## 修 Bug B1-B3

### B1 根因报告（五阶段调查）

**Iron Law：没找到根因，禁止提修复方案。**

按 `templates/bug-report.md` 产出根因报告（目录从仓库约定，默认 `docs/bugs/<slug>/root-cause.md`），五阶段按序完成：

1. **读错误信息**：完整读堆栈 / 日志，记下行号、文件、错误码
2. **复现**：稳定复现路径；复现不了就先收集线索，不猜
3. **查近期变更**：git diff / 最近提交 / 配置变更
4. **跨组件边界取证**：涉及跨服务 / 跨组件链路时，先在边界处取证据（调用入参返回 / 数据落库状态），定位失效组件后再深入
5. **正常样本对照**：找同库能跑的类似实现 / 正常数据，与故障样本逐条列差异，不假设「这个无所谓」

【用户未确认根因前，禁止改任何代码。】

### B2 最小修复

最小修改原则，不顺手重构。

假设一次只验证一个变量；修复尝试失败 2 次回到 B1 重查，3 次以上质疑设计（架构 / 模式选错），不再继续打补丁。

### B3 验证

「改了代码」≠「修好了」。按 B1 写好的验证方案执行，结论三选一：verified / partial / failed。没有验证证据就不算修好。

## 借鉴来源（版本基准）

本 skill 对以下仓库为**思想借鉴，无代码依赖**，上游升级不要求同步；仅当上游方法论大改版时（如粒度定义 / 验证规则 / 调查流程重构），人工看 release notes 决定是否吸收，核对后更新此处版本号：

- [obra/superpowers](https://github.com/obra/superpowers) `v7.0.2`（2026-11-03）：writing-plans 的「写给没见过代码库的工程师」、任务粒度与交付前自检（G3/G4）；systematic-debugging 的根因铁律、调查阶段、组件边界取证、正常样本对照与假设验证纪律（B1/B2）；verification-before-completion 的验证铁律与借口对照表（G5/B3）；brainstorming 的回放确认、澄清纪律与动态升档（G1/G4）；executing-plans 的裁决落盘、进度台账与审查分级处置（G4/G6）
- [github/spec-kit](https://github.com/github/spec-kit) `v1.4.4`（2026-11-23）：spec 的用户故事 + EARS 验收标准结构与稳定编号追溯（G2/G3/G5）；bug 三步 assess→fix→test 模型（B1-B3）；clarify 的问题预算、回写不留矛盾与模糊词量化（G1/G2）；converge 的完成声明非证据、全量重验与四类差距（G5）
