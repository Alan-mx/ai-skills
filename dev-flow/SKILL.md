# 开发流水线（强制关口·通用核心）

## 入口判断

- 新需求（PRD / 原型 / 口头功能描述要开发）→ 走 G1-G6
- 缺陷 / 异常行为 → 走 B1-B3
- 一句话且信息完整的小改动（改文案 / 调样式）→ 不走关口，直接做
- 分不清 → 先问用户

每个关口的产物须用户 review 通过才进下一关。【禁止跳关、禁止合并关口、禁止关口产物只停留在对话里不落盘。】

## 仓库适配

本 skill 是通用核心。文中「仓库规范」指当前仓库根目录 `AGENTS.md` / `CLAUDE.md` 的对应内容（编码规范、构建命令、接口文档要求、自查清单、镜像仓库同步要求等）；仓库没有约定的，按业界常规执行并在产物里注明所采用的口径。

## 新需求 G1-G6

### G1 需求澄清

读 PRD / 原型，并搜索现有实现，按 `templates/clarify.md` 产出疑问清单（歧义 / 缺失 / 与现有逻辑冲突 三类，每条附建议默认答案供用户快速拍板）。

【用户未逐条回答前，禁止进入 G2。】

### G2 规格化

按 `templates/spec.md` 产出规格文档（目录从仓库约定，默认 `docs/specs/<需求名>/spec.md`）：用户故事 + 验收标准（EARS 写法：WHEN〈触发〉THE SYSTEM SHALL〈响应〉）+ 字段口径 + 状态流转 + 权限 + 非目标。

【用户未确认 spec 前，禁止进入 G3。】

### G3 设计（顺序强制：先数据结构后接口）

先搜索现有实现与可复用点（优先复用，不重造），再按 `templates/design.md` 分两步产出，每步单独确认：

1. **表 / 数据结构设计**：DDL 草案（新增 / 变更）→ 用户确认
2. **接口清单**：方法 / 路径 / 职责 / 入出参概要 + 实现任务清单 → 用户确认

设计文档写作标准：**写给一个没见过这个代码库的工程师**——写清「你做的决定」（动哪个文件、什么签名、哪张表、每个接口对应哪个任务），不写泛泛而谈的步骤。

【数据结构未经确认，禁止出接口清单；两者未确认，禁止进入 G4。】

### G3.5 工作量评估（用户要求或排期需要时，不阻塞开发）

按 `templates/estimate.md` 产出简版评估，口径：

- **人 + AI 协作**的工作量（非纯人工口径，AI 提效已计入——纯人工 2 天的 CRUD，人+AI 约 0.5 天）
- 逐功能列条目，粒度 **0.2 ~ 1 天/条**，格式「1. xxx功能 x天」，不搞复杂度矩阵
- 固定 **+1 天缓冲**（防完不成的兜底，给自己留的）
- leader 给了参考时间的注明对照，没给就不写
- **核心输出：预计完成日期**（今天 + 总天数 → 具体日期），这是唯一重要结论
- 评估前查历史 estimate.md 的回填数据校准手感；完工后回填实际天数

### G4 实现（垂直切片，禁止层批量）

任务粒度：**一个 reviewer 能独立否决的最小单元**（即一个接口的一条完整切片），每步是一个可检查的动作。

1. **数据结构落地**：DDL / 迁移脚本写成文件交用户手动执行（AI 不直接改库），ORM 实体 / VO / DTO / 映射全链路同步（按仓库约定）
2. **接口逐个实现**：每个接口走完整垂直切片——数据层 → 服务层 → 接口层 → 接口文档（按仓库规范），完成后立即用仓库约定的构建命令编译验证 + 自查清单，通过再做下一个接口
3. 【禁止】先建完全部实体再铺全部接口、一次性生成一大批接口代码。复杂接口（状态机 / 审批 / 消息 / 金额）必须单个走；同质简单 CRUD 默认也逐个，用户明确说「这几个一起做」才可合并
4. 全程遵守仓库编码规范与最小修改原则

### G5 收敛检查（验证铁律）

**Iron Law：没有新鲜的验证证据，不得声称任何一项完成。**

对照 G2 spec 的验收标准逐条核对，出差距报告：未实现 / 实现偏差 / 超出范围（scope creep）。

| 常见借口 | 现实 |
|---|---|
| 「应该可以了 / 应该没问题」 | 跑验证拿证据 |
| 「代码改了，逻辑上对」 | 编译输出 / 查询结果才算数 |
| 「上个任务验证过了」 | 每个声称都要本次证据 |

【未全部通过，打回 G4，禁止进入 G6。】

### G6 提交

代码审查（有 `/code-review` 类命令则跑，否则按审查清单自查）→ 汇总改动与验证结果 → **询问用户是否提交 git，不得自行 commit / push**。

## 修 Bug B1-B3

### B1 根因报告（四阶段调查）

**Iron Law：没找到根因，禁止提修复方案。**

按 `templates/bug-report.md` 产出根因报告（目录从仓库约定，默认 `docs/bugs/<slug>/root-cause.md`），四阶段按序完成：

1. **读错误信息**：完整读堆栈 / 日志，记下行号、文件、错误码
2. **复现**：稳定复现路径；复现不了就先收集线索，不猜
3. **查近期变更**：git diff / 最近提交 / 配置变更
4. **跨组件边界取证**：涉及跨服务 / 跨组件链路时，先在边界处取证据（调用入参返回 / 数据落库状态），定位失效组件后再深入

【用户未确认根因前，禁止改任何代码。】

### B2 最小修复

最小修改原则，不顺手重构。

### B3 验证

「改了代码」≠「修好了」。按 B1 写好的验证方案执行，结论三选一：verified / partial / failed。没有验证证据就不算修好。

## 借鉴来源（版本基准）

本 skill 对以下仓库为**思想借鉴，无代码依赖**，上游升级不要求同步；仅当上游方法论大改版时（如粒度定义 / 验证规则 / 调查流程重构），人工看 release notes 决定是否吸收，吸收后更新此处版本号：

- [obra/superpowers](https://github.com/obra/superpowers) `v7.0.0`（2026-10-10）：writing-plans 的「写给没见过代码库的工程师」与任务粒度定义（G3/G4）；systematic-debugging 的根因铁律、四阶段与组件边界取证（B1）；verification-before-completion 的验证铁律与借口对照表（G5/B3）
- [github/spec-kit](https://github.com/github/spec-kit) `v1.1.3`（2026-10-09）：spec 的用户故事 + EARS 验收标准结构（G2）；bug 三步 assess→fix→test 模型（B1-B3）
