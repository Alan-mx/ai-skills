# Freebuff 委派

本 skill 不绑定 Codex。下文“主控 Agent”指当前调用本 skill 的执行者，包括 Codex、Claude Code 或其他能启动并读写终端进程的 Agent。

把 Freebuff 当作低频、可选、受监督且额度稀缺的编码执行者，而不是可信的最终决策者。默认由主控 Agent 直接完成任务；用户明确要求启动时，主控 Agent 应执行，但任务完成责任仍由主控 Agent 承担。

## 角色契约

- 主控 Agent 是总控：负责需求理解、澄清、设计与验收标准、任务拆分、派单、进度控制、独立验证、纠偏、接管和最终汇报。
- Freebuff 是执行者：只在主控 Agent 下发的工作包内检查代码、实现和运行指定命令；它不拥有需求解释权，也不能自行决定范围、架构、数据结构、接口或“已完成”。
- Freebuff 不常驻，也不参与整个任务链。通常一天只规划一次；尽量按预先计划完成，完成后退出并验收。
- 同一账号并发通常为 1。启动前先检查已有 Freebuff 进程；禁止并行启动，必须串行使用。
- Freebuff 失败或偏离时，主控 Agent 先收窄问题重试；达到停止条件仍失败就接管实现，不能把失败原样退回给用户。
- 只有用户明确要求使用 Freebuff 或显式调用本 skill 时才启用；支持 `$` 调用的宿主等价于 `$freebuff-delegate`。
- 用户要求启动后，主控 Agent 可以提示性价比、额度或风险，但不能因此擅自否决。只有额度不足、已有并发会话、隐私/密钥硬边界或技术前置不满足时才停止并说明。

## 适用判断

优先委派：

- 任务体量较大，但边界清楚、可隔离、可独立验收。
- 主控 Agent 已完成设计和验收定义，任务的预期工作量足以利用一段完整会话。
- Freebuff 只需执行预先排好的一个垂直切片或少量相关切片。
- 数据允许交给第三方，且 Freebuff 额度可用。

一般优先由主控 Agent 直接完成：

- 小型修改、高耦合改动、需要频繁往返确认的任务。
- 需求或设计尚未稳定，无法一次写清执行包。
- 需要接触个人信息、凭据、生产密钥或未获授权的数据。

## 额度与并发

- 额度是稀缺预算。当前账号界面可能显示每天约 `25 Freebucks`，某些模型的一小时会话可能扣除约 `15`；实际余额、模型价格和可用模式以界面为准。
- 第一条消息就会开始一次会话。发送前必须确认：模型价格可承受、任务计划已冻结、工作区已准备、验收命令已确定、预计能在可用时长内完成。
- `15 Freebucks/hour` 是模型的一小时预授权/封顶价，不是按墙钟时间固定扣满 15。第一条消息先预留价格，`/end-session` 或 `✕ End session` 后由服务端按实际用量结算并退回未使用部分。
- 实际结算可能综合模型、工具、子代理等用量，token 只是可能的成本来源之一；客户端未公开精确的 token→Freebucks 换算。短任务可能有最低 1 个 Freebuck 或向上取整。
- 不要用剩余分钟估算花费。实测两次短会话净消耗均为 `1 Freebuck`，即使界面还剩约 23 分钟也不按分钟线性扣费；可靠方式是记录 `/end-session` 前后的余额差值。
- 执行 `stop` 只关闭本地进程，不退款且服务端倒计时继续；完成任务后必须用 `/end-session` 或 `✕ End session` 结算。
- 禁止为了试探、闲聊、问小问题或验证 Freebuff 是否能做而启动会话；这些直接由主控 Agent 完成。
- 不建议把 25 个积分拆成多次低价值会话；`End session` 会退出未使用部分，退款后是否能在同一天再次启动取决于余额和模型价格。
- 并发限制为 1。已有 Freebuff 正在运行时，不得另开窗口；仅在同一个已规划任务内继续交互。
- 一次会话优先完成一个完整执行计划。若计划包含少量相关切片，主控 Agent 预先固定顺序和逐切片验收点；用户可随时调整或终止。

## 会话装填与时间盒（建议）

**尽量 Session-ready**：优先让排队任务预计填满 45–60 分钟，并提前完成设计、澄清、接口定义、环境安装和基线测试。这只是提高性价比的建议，不是启动门槛。

用户要求启动且额度、并发、隐私和技术前置都满足时，即使队列更短也要执行；主控 Agent 可以说明预估利用率，但由用户决定是否接受。

**建议一次会话装一个任务队列**：避免为多个小任务反复开窗。会话内可按预设顺序执行多个垂直切片：

- T1：目标、允许改动范围、验收标准。
- T2：同上。
- T3：同上。

每个切片完成后，主控 Agent 立即检查 diff 和验证结果，通过后再喂下一个。

**建议时间盒**（可调整，不强制执行）：

- 0–5 分钟：确认模型、额度和干净基线。
- 5–45 分钟：连续执行队列中的实现任务。
- 45–55 分钟：运行完整测试并修补回归。
- 55–60 分钟：汇总改动并停止。

如果提前完成，优先继续执行预先写好的任务；用户要求探索新任务时，再先确认范围。时间盒只用于防止无边界拖延，不覆盖用户指令。

**匹配高价值执行任务**：

- 适合：多文件但规格清楚的机械实现、大量重复修改、迁移和测试修补、已有设计后的垂直切片。
- 不适合：需求澄清、架构或接口决策、小型修改、高耦合调试、需要频繁确认的任务、个人信息。

**主控 Agent 负责前后两端**：开始前准备 worktree、任务包、测试命令和回滚点；结束后独立 review、跑测试、修残余问题。Freebuff 失败两轮就由主控 Agent 接管，避免把一小时烧在反复试错上。

## 隐私与数据边界

- Freebuff 可能将数据用于 AI 训练。个人信息默认禁止交给 Freebuff，包括真实姓名、手机号、邮箱、证件号、住址、学号/工号、学校/单位、账号标识、健康或财务信息、客户个人信息、私人聊天和照片。
- 其他非个人信息的代码、业务数据、测试数据、接口和文档，可在用户授权且仓库规则允许时委派，不必因非个人信息而一律拒绝。
- 凭据、私钥、生产令牌、可用密钥、数据库导出和生产敏感数据始终禁止交给 Freebuff；与是否属于个人信息无关。
- 存在个人信息时，主控 Agent 先脱敏、扫描复核，或者直接由主控 Agent 完成，不把原始数据交给 Freebuff。
- 委派时使用独立 worktree 或专用临时目录，并在任务包中限制允许访问的路径。

## 工作流衔接

- 当前仓库适用 `dev-flow` 时，主控 Agent 完成 G1-G3，并保留 G5 收敛验证、G6 提交决策；Freebuff 只执行 G4 中已确认的垂直切片。
- Freebuff 不会自动继承主控 Agent 的 skill 或关口状态。主控 Agent 必须把目标、验收标准、非目标、允许改动范围和验证命令写进任务包。
- 是否满足流程由主控 Agent 对照仓库约定和验收标准检查，不能依赖 Freebuff 自报。

## 启动前

1. 使用宿主环境的命令检查方式确认 `freebuff` 可执行并运行版本命令；例如 PowerShell 的 `Get-Command`、POSIX shell 的 `command -v` 或 Windows `where`。若命令不存在，停止并说明；若要求登录，让用户完成登录，不代填或读取凭据。
2. 优先在独立 Git worktree 或专用临时目录中执行。若必须在现有目录执行，先记录 `git status --short`、当前提交和已有改动。
3. 检查目标仓库是否含 `.agents` 或 `mcp.json`。不要主动使用 `--trust-agents`；只有用户明确授权且已确认这些配置可信时才加该参数。
4. 每个任务包至少包含：
   - 目标、验收标准、非目标、允许修改的路径或模块。
   - 当前仓库的构建、测试和静态检查命令；解释器/运行时可能命中别名时写明确的可执行路径。
   - “不要 commit、push、改无关文件、访问凭据或扩大范围”。
   - 遇到阻塞先报告，不猜测；完成后列出改动文件和已执行的验证命令。
   - 停止条件：测试失败、命令失败、需要扩大范围或需要新凭据时立即停止并报告。

一个任务包默认只覆盖一个可独立审查的垂直切片。一次会话内执行多个切片时，只允许执行主控 Agent 预先写好的顺序，不现场扩张。

## 终端接入

Windows 默认使用本 skill 的 ConPTY 包装器：

```text
scripts/freebuff_conpty.py
```

- 包装器持有 Freebuff 子进程的 ConPTY 输入输出，不依赖前台焦点，不使用全局 `SendInput`。
- 主控 Agent 通过 `start`、`send`、`key`、`status`、`wait`、`stop` 操作；任何能运行 shell 的 Agent 都可以调用。
- `stop` 只结束本地包装器进程，不退款也不结束服务端会话；应通过 `/end-session` 或 `✕ End session` 正式结束并退回未使用积分。
- 第一次使用先运行 `setup` 安装本地 `pywinpty` 依赖；详细命令和故障恢复读取 [references/windows.md](references/windows.md)。
- `SendInput` 只作为包装器不可用时的兜底，而且必须在每一次注入前确认目标窗口仍是前台；详细约束见 Windows reference。

其他宿主直接使用自身的 PTY 或等价交互式终端能力。Freebuff 没有稳定的一次性 prompt 参数；启动当前执行包，按界面提示发送任务，完成后退出。

## 总控循环

1. 主控 Agent 冻结当前切片的输入、验收和允许改动范围。
2. 派给 Freebuff 一个任务包，等待它停止或提问。
3. 主控 Agent 检查实际 diff，并运行仓库要求的验证命令。
4. 不通过时，优先在同一个会话内发出更窄的纠正任务；连续两轮仍失败则停止派单并由主控 Agent 接管。
5. 当前切片通过后，只执行已排好的下一项；计划完成后退出会话并收敛最终结果。

## Token 控制

- 不把每一帧终端重绘或整屏广告反复读进上下文。
- 优先用包装器的 `wait` 和受限 `status --tail` 获取状态；任务结束后用 `git diff --stat`、聚焦 diff 和测试结果复核。
- 任务包只提供 Freebuff 自己难以发现的上下文，让它自行阅读仓库；不要复制大段代码进提示。
- 小型或高度耦合的修改直接由主控 Agent 完成通常更省 token 和额度。

## 独立复核

- 对比启动前后的 `git status` 和 `git diff`，确认改动只落在授权范围。
- 阅读实际差异，检查逻辑、兼容性、安全和越界修改；不要仅复述 Freebuff 的总结。
- 运行仓库原有构建、测试或最小可复现验证。无法验证时明确标记 `partial` 或 `failed`。
- 如 Freebuff 改坏非目标内容，只回退本次授权范围内的改动；不得回退来源不明或用户已有的改动。
- 汇报实际改动、独立验证证据、未验证项、额度与数据边界风险。

## Git 边界

Freebuff 和本 skill 都不得自行 commit 或 push。除非用户在当前任务中单独明确授权，只保留工作区改动并汇报。
