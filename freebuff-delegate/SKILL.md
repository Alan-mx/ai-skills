# Freebuff 委派

本 skill 不绑定 Codex。下文“主控 Agent”指当前调用本 skill 的执行者，包括 Codex、Claude Code 或其他能启动并读写终端进程的 Agent；宿主具备 PTY 或等价交互式终端能力即可使用。

把 Freebuff 当作低频、可选、受监督且额度稀缺的编码执行者，而不是可信的最终决策者。默认由主控 Agent 直接完成任务；只有明确要求且任务值得消耗一段会话时，才派 Freebuff 干活，但不能把完成责任转给它。

## 角色契约

- 主控 Agent 是总控：负责需求理解、澄清、设计与验收标准、任务拆分、派单、进度控制、独立验证、纠偏、接管和最终汇报。
- Freebuff 是执行者：只在主控 Agent 下发的工作包内检查代码、实现和运行指定命令；它不拥有需求解释权，也不能自行决定范围、架构、数据结构、接口或“已完成”。
- Freebuff 不常驻，也不参与整个任务链。通常一天只规划一次；一次启动就要完成预先设计好的执行计划，完成后退出并验收。
- Freebuff 失败或偏离时，主控 Agent 先收窄问题重试；达到停止条件仍失败就接管实现，不能把失败原样退回给用户。
- 只有用户明确要求使用 Freebuff 或显式调用本 skill 时才评估是否启动；支持 `$` 调用的宿主等价于 `$freebuff-delegate`。即使用户提出，主控 Agent 判断委派成本高于直接完成时也可以不派，并说明原因。
- 同一账号并发通常为 1。启动前先确认没有其他 Freebuff 窗口或子进程；禁止并行启动，必须串行使用。
- 越界、敏感数据、外部副作用或必须用户决策时停下来确认。

## 适用判断

优先委派：

- 任务体量较大，但边界清楚、可隔离、可独立验收。
- 主控 Agent 已完成设计和验收定义，任务的预期工作量足以利用一段完整会话。
- Freebuff 只需执行预先排好的一个垂直切片或少量相关切片。
- 数据允许交给第三方，且 Freebuff 额度可用。

直接由主控 Agent 完成：

- 小型修改、高耦合改动、需要频繁往返确认的任务。
- 需求或设计尚未稳定，无法一次写清执行包。
- 需要接触凭据、隐私、生产数据或不允许用于 AI 训练的内容。

## 额度与并发

- 额度是稀缺预算，不是可以反复试用的资源。当前账号界面可能显示每天约 `25 Freebucks`，某些模型的一小时会话可能扣除约 `15`；实际余额、模型价格和可用模式以界面为准。
- 第一条消息就会开始一次会话。发送前必须确认：模型价格可承受、任务计划已冻结、工作区已准备、验收命令已确定、预计能在可用时长内完成。
- 禁止为了试探、闲聊、问小问题或验证 Freebuff 是否能做而启动会话；这些直接由主控 Agent 完成。
- 默认每天最多启动一次 Freebuff。只有任务价值足够高且当天额度允许时才使用，不把 25 个积分拆成多次低价值会话。
- 并发限制为 1。已有 Freebuff 正在运行时，不得另开窗口；仅在同一个已规划任务内继续交互，任务结束或有明确阻断后再退出。
- 一次会话优先完成一个完整执行计划。若计划包含少量相关切片，主控 Agent 必须预先固定顺序和逐切片验收点，不能让 Freebuff 自行扩大范围。

## 启动边界

- 启动前确认任务范围清楚、目标目录明确、验收方式可执行。范围过大时先拆成可独立审查的子任务。
- Freebuff 界面明确提示可能将数据用于 AI 训练。不要把凭据、私钥、生产令牌、客户隐私数据、数据库导出或未获授权的私有代码交给它；不确定时先问用户。
- 额度绑定 Freebuff 账号和当前网络。启动前检查现有进程和可用额度；启动后再次确认剩余 Freebucks、模型价格与可用模式，并向用户说明本次委派会消耗同一份额度。

## 工作流衔接

- 当前仓库适用 `dev-flow` 时，主控 Agent 完成 G1-G3，并保留 G5 收敛验证、G6 提交决策；Freebuff 只执行 G4 中已确认的垂直切片。工作量评估也由主控 Agent 负责。
- Freebuff 不会自动继承主控 Agent 的 skill 或关口状态。主控 Agent 必须把当前切片的目标、验收标准、非目标和验证命令写进任务包。
- Freebuff 可以读取仓库规则，但不能假定它已正确理解或遵守。是否满足流程由主控 Agent 对照仓库约定和验收标准检查。

## 启动前

1. 使用宿主环境的命令检查方式确认 `freebuff` 可执行并运行版本命令；例如 PowerShell 的 `Get-Command`、POSIX shell 的 `command -v` 或 Windows `where`。若命令不存在，停止并说明；若要求登录，让用户完成登录，不代填或读取凭据。
2. 优先在独立 Git worktree 或专用临时目录中执行。若必须在现有目录执行，先记录 `git status --short`、当前提交和已有改动，不能把用户原有改动误归因于 Freebuff。
3. 检查目标仓库是否含 `.agents` 或 `mcp.json`。不要主动使用 `--trust-agents`；只有用户明确授权且已确认这些配置可信时才加该参数。
4. 每个任务包至少包含：
   - 目标、验收标准、非目标、允许修改的路径或模块。
   - 当前仓库的构建、测试和静态检查命令。
   - “不要 commit、push、改无关文件、访问凭据或扩大范围”。
   - 遇到阻塞先报告，不猜测；完成后列出改动文件和已执行的验证命令。
   - 停止条件：测试失败、命令失败、需要扩大范围或需要新凭据时立即停止并报告。

一个任务包默认只覆盖一个可独立审查的垂直切片，不把整个模块或整批接口一次性交给 Freebuff。一次会话内执行多个切片时，只允许执行主控 Agent 预先写好的顺序，不现场扩张。

## PTY 交互

Freebuff 是交互式 TUI，没有稳定的一次性 prompt 参数。使用宿主 Agent 的 PTY、终端会话或等价交互式终端能力；例如 Codex 可用 `exec_command(tty: true)` 配合 `write_stdin`，其他宿主使用自身的终端启动、输入和读取能力。宿主没有原生 PTY 时，可使用平台上的伪终端包装工具，但不得把需要 TTY 的 TUI 当作普通非交互管道运行。

1. 启动当前执行包的交互式终端：

   ```text
   freebuff --cwd <绝对路径>
   ```

2. 通过宿主的终端输入能力发送任务，按界面的实际提示继续交互。需要继续已有会话时，按帮助信息使用 `freebuff --continue [conversation-id]`。
3. 把连续输出视为过程信息，不把 Freebuff 的“完成”声明当作证据。若它提出问题，只在用户已授权的范围内回答；涉及敏感数据、扩大范围或外部副作用时回到用户确认。
4. 优先用界面的 `/exit` 命令退出。若 TUI 未退出，只终止本次 Freebuff 子进程，不终止无关 Node 或其他 Agent 进程。

## 总控循环

1. 主控 Agent 冻结当前切片的输入、验收和允许改动范围。
2. 派给 Freebuff 一个任务包，等待它停止或提问。
3. 主控 Agent 检查实际 diff，并运行仓库要求的验证命令。
4. 不通过时，主控 Agent 优先在同一个会话内发出更窄的纠正任务；连续两轮仍失败则停止派单并由主控 Agent 接管。
5. 当前切片通过后，只执行主控 Agent 已排好的下一项；计划完成后退出会话，由主控 Agent 收敛并给出最终验证结果。

## Token 控制

- Freebuff 消耗自己的 Freebucks；主控 Agent 的主要开销来自 TUI 输出、任务包、diff 和测试结果。不要把每一帧终端重绘都反复读进上下文。
- 等待完成时减少无效轮询并限制单次输出；结束后优先用 `git diff --stat`、聚焦 diff 和测试结果复核。
- 任务包只提供 Freebuff 自己难以发现的上下文，让它自行阅读仓库；不要为了派单把大段代码复制进提示。
- 小型或高度耦合的修改直接由主控 Agent 完成通常更省 token 和额度；只有在任务可隔离、执行包清晰时才值得委派。

## 独立复核

- 对比启动前后的 `git status` 和 `git diff`，确认改动只落在授权范围。
- 阅读实际差异，检查逻辑、兼容性、安全和越界修改；不要仅复述 Freebuff 的总结。
- 运行仓库原有构建、测试或最小可复现验证。无法验证时明确标记 `partial` 或 `failed`，不要声称完成。
- 在隔离 worktree 中，如发现 Freebuff 改坏了非目标内容，可只回退它造成的改动；在共享目录中不得自行回退来源不明或用户已有的改动。
- 汇报以下内容：Freebuff 实际改动、主控 Agent 的独立验证证据、未验证项、额度与数据边界风险、是否需要用户继续决策。

## Git 边界

Freebuff 和本 skill 都不得自行 commit 或 push。除非用户在当前任务中单独明确授权，只保留工作区改动并汇报。
